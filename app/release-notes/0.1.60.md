## What is in this build

### Store listing: a Zusammenfassung screenshot, and tablet sets

The listing showed four phone screenshots and stopped before the screen that
answers the user's actual question. A fifth shot now covers the summary: the
Brutto scenario totals, the Jahresrichtwert for sport/green areas, the
alternative-water deduction, the Netto-Antragsmenge and the PDF export.

Play keeps phone, 7-inch and 10-inch screenshots as three separate image kinds,
and only the phone kind was ever supplied. `scripts/captureScreenshots.mjs` now
captures all three (`--devices` selects a subset) into the directories
`deployAndroid.py`'s `IMAGE_KINDS` already expected, so no change was needed on
the publishing side.

Each device is captured at a real device CSS size rather than the output pixel
size — layout follows CSS width, so rendering at output width would file a
desktop screenshot under "phone". 10-inch is landscape (1280x800 CSS): portrait
at 800 CSS px sits below the 900px nav breakpoint and produced markedly more
empty space.

The summary's per-area table lives in a collapsed `<details>`, so shots gained a
`prepare` hook to open it and a `scrollTo` to anchor the section, which is below
the fold. It is opened only where it fits: at 360 px the table scrolls
horizontally (numbers cut mid-digit) and its two footnotes push the
Netto-Antragsmenge and the PDF button off-screen, so the phone shot shows it
closed and the tablets expanded.

### Seed fix: the golf assignment produced no result

The screenshot seed set `golfAreaMode: "18hole"` without `golfGreensM2` /
`golfTeeM2` / `golfFairwayM2`. The mode is only the UI shortcut that fills those
three values (`TABLE_35` in `golf.ts`, applied by the mode buttons in
`AssignmentPage`); `getAssignmentResult` dispatches on the values themselves. The
seed therefore stored a combination the app never stores, `getAssignmentResult`
returned `null`, and the golf row rendered an empty "–" in the summary — and no
result pills on the scenario page.

This fails as plausible layout rather than as an error, so the capture script now
asserts every summary row carries a scenario value and aborts if one does not.
That is the same class of trap as the existing ErrorBoundary check.

### Summary card: one gutter for every child

Two direct children of `.project-summary` had drifted off the 14px inset the
other rows use: `__table-footnote` (margin, no horizontal padding) and the
embedded `InfoHint` (a shared component carrying none of its own). Both read as a
step in the card's text column, most visibly at tablet widths where the card is
wide.

Fixed at the shared ancestor rather than per element: the gutter is now named
once as `--summary-gutter` on `.project-summary`, and the children reference it,
so the card supplies the inset for an embedded component instead of that
component hard-coding a page-specific value.

## Validation

  2560x1600, all within 320–3840 px per edge and under the 2:1 ratio cap.
- `deployAndroid.py --dry-run` confirmed all three kinds are picked up.
