## What is in this build

- **The installed app updates itself again instead of needing „Aktualisieren".**
  The reload-loop guard in `App.tsx` was a bare `sessionStorage` flag: once set,
  the silent recovery never ran again *for the life of the session*.

  A browser tab survives that, because the session ends when the tab closes. An
  installed PWA has one session spanning many deploys — so after the first time
  the guard fired, the app permanently lost the ability to update itself, and the
  only remaining route to a new version was pressing the button. Reported from a
  phone sitting on 0.1.55 where reloading changed nothing.

  The key now records *which version* the recovery was attempted for
  (`dwa_sw_recovery_attempted_for`), so every new deploy re-arms it while a
  genuinely unreconcilable mismatch still reloads only once.

### Why updating felt complicated at all

Two independent things, and it is worth writing down because the symptom recurred
across several releases:

1. **`registerType: 'prompt'`** (vite-plugin-pwa) means a newly installed worker
   goes to `waiting` and stays there. A plain reload cannot help: the old worker
   still controls the page and answers the reload from its own cache. Only
   `skipWaiting()` — what the „Aktualisieren" button calls — moves it along.
2. The startup guard exists precisely to call that automatically, so the button
   should be a fallback rather than the normal path. It had disarmed itself.

With (2) fixed, the intended behaviour is back: a mismatch found at startup is
resolved silently, and the banner is reserved for a deploy that lands while the
app is open.
