## What is in this build

Follow-up to 0.1.45, which fixed the *cause* of the stale-cache error but not the
situation of a user already in it.

- **Recovery from a stuck service worker, without Shift-Reload** (`44ba3c4`, web
  only — the native shell registers no worker). 0.1.45 stopped the SPA fallback
  answering `/data/` requests, but a client already carrying the old worker could
  end up with:
  - the "Laden fehlgeschlagen" error, **and**
  - no "Update verfügbar" banner, because nothing was `waiting` so `needRefresh`
    never became true.

  The only way out was Shift-Reload — a plain reload cannot help, since the stale
  worker answers the reload from its own cache. Not something a user can be
  expected to know.

  Three routes out now exist, ordered so that as few users as possible notice
  anything:
  1. **Automatic.** When the initial load fails, the app performs the reset once
     by itself and reloads. A `sessionStorage` flag makes it strictly one attempt,
     so a genuinely broken deploy shows the error rather than reload-looping. The
     flag is cleared on every successful load, so a later failure can self-heal
     again.
  2. **The error screen** keeps its explicit **Neu laden** button (added in
     0.1.45).
  3. **"Über die App" → "App neu laden (Zwischenspeicher leeren)"**, always
     visible. This covers the case where the app loads but is otherwise stale —
     there is no error screen to reach then, and the update check alone could only
     *report* the state, not fix it.

  All three share `hardResetAndReload()`: unregister every service worker, delete
  every cache, reload. **`localStorage` is untouched**, so farms, fields,
  scenarios and assignments survive — the hint under the button says so.

  The "Auf Updates prüfen" wording was also corrected: it previously pointed at
  the update banner, which in exactly this situation is not shown.
