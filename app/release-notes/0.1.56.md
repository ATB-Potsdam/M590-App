## What is in this build

- **The installed app no longer scrolls on a page that fits.** In a standalone
  PWA on Android, both `100vh` and `100dvh` resolve against the **screen**, while
  `window.innerHeight` excludes the system navigation/gesture bar. `body` was
  therefore floored at 803 px inside a 747 px viewport — 56 px of empty,
  scrollable page that no element occupied, which also kept the scroll shadow
  above the logo bar permanently visible.

  Now `html { height: 100% }` + `body { min-height: 100% }`. Percentages resolve
  against the containing block, which follows the real viewport, so there is no
  unit-resolution ambiguity to get wrong.

### How it was actually found

Three wrong guesses first, all of them reasoned rather than measured:

1. `.page` bottom padding — checked, correct at 108 px (64 nav + 28 logo bar + 16).
2. `100vh` → `100dvh` (shipped as 0.1.55) — **could not have helped.** A PWA has
   no URL bar, so `dvh` and `vh` are identical in standalone. This was shipped
   without first asking where the problem appeared.
3. Safe-area inset counted twice — real in principle, but the device reports
   `env(safe-area-inset-bottom)` as `0px`, so it was not this either.

What settled it was data from the device: `scrollHeight` 803 vs `innerHeight`
747, and a scan for non-fixed elements extending below the fold returned an
**empty list**. No content was overflowing, so the height had to come from the
scrolling box itself — which is the `min-height` floor.

The lesson worth keeping: a symptom that only appears in one display mode should
be measured in that display mode before anything is changed.
