## What is in this build

One fix, found by using 0.1.49 rather than by testing it.

- **The update banner no longer appears when the version has not changed**
  (`4f20ab4`). Every deploy rewrites `sw.js` — the precache manifest hashes move
  even when no user-visible file did — so redeploying the *same* release still
  installed a new service worker, and the `updatefound` listener offered every
  open session an update to the version it was already running.

  Observed directly after the 0.1.49 deploy: a tab running 0.1.49, with the new
  code demonstrably active (`.nav-bar-wrapper` and `.result-pill--yearly` both
  present in the DOM), showing „Update verfügbar" for 0.1.49.

  The banner now asks the server what it serves and stays silent when that
  matches the running build. `data/version.json` is excluded from the precache
  (`globIgnores: ['data/**']`), so the answer comes from the network rather than
  from the cache being questioned.

  Two deliberate choices in the check:
  - **A null answer still shows the banner.** `fetchServerVersion()` returns null
    on any doubt — offline, malformed JSON, an HTML fallback from a stale worker.
    An unreachable server must not be able to hide a genuine update, so
    uncertainty resolves towards prompting.
  - **Suppressing leaves the new worker `waiting`**, since `registerType` is
    `'prompt'` and nothing calls `skipWaiting()` for it. That is harmless
    precisely because of what was just checked: it precaches the same version, so
    whether it takes over on a later load or keeps waiting, the assets are
    equivalent. Nobody ends up stranded on stale content because of a prompt that
    was withheld.

## Why this was not caught in 0.1.47/0.1.48

Those releases fixed the *other* half of the same area: a version mismatch **at
page load** used to produce a banner, and now recovers silently (`App.tsx`). The
two paths remain deliberately different — a mismatch at startup is resolved
without asking, a deploy landing **mid-session** asks first.

What neither release considered is that "a new worker installed" and "a new
version exists" are not the same statement. The mid-session path took the first
as evidence of the second. It only becomes visible when the same version is
deployed twice with a session open, which is exactly what a day of deploying
does and what a release test does not.
