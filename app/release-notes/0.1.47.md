# Release notes — 0.1.47

Previous release: 0.1.46 (see [0.1.46.md](0.1.46.md)). Its bundle was built but
never uploaded, and at the time versionCode was hand-edited so this release would
reuse the same number. That practice has since been dropped — see
`scripts/buildAndroid.sh`: the build bumps versionCode unconditionally, gaps in
the sequence are harmless, and hand-editing risks a duplicate that only fails at
upload time.

Every release build raises versionCode (see `scripts/buildAndroid.sh`), so read
the actual number from the build output rather than trusting any figure here.

## What is in this build

Two changes: the last piece of the stale-cache work, and the chapter references
brought in line with the corrected proof.

- **A stale bundle is now detected by version and recovered silently**
  (`02fa2e6`, web only — the native shell registers no service worker). 0.1.45
  and 0.1.46 fixed the cause and added manual recovery, but nothing could *notice*
  that a client was running the wrong version in the first place.

  `__APP_VERSION__` is inlined at build time, so a stale client reports the old
  version and has nothing to compare against. The build therefore emits
  `data/version.json` carrying the version it was cut from — placed under `data/`
  because that is the one directory excluded from the service-worker precache, so
  even a stale client reads it from the network.

  Two detectors, cheapest first:
  1. **Downgrade.** The version of each successful load is recorded in
     `localStorage`. If a later start comes up *older* than what last ran on this
     device, only a stale cache can explain it — no network needed. (Captured at
     module-import time: reading it lazily would race the successful-load write
     and always see the current version.)
  2. **Server mismatch.** Otherwise `data/version.json` is compared, and acted on
     only when no update is already staged, so the ordinary update path keeps
     priority.

  Either one triggers the reset-and-reload once per tab.

- **Update banner reserved for mid-session deploys.** A mismatch that exists at
  startup now reloads silently instead of raising a banner for a change the user
  never saw. The banner is left to the `updatefound` listener — i.e. a deploy that
  lands while the app is open, which is the case that genuinely warrants asking.

- **Chapter references follow the May 2026 corrected proof** (`8d4d8c5`, web and
  native). The Korrekturfahne of 28 May 2026 inserts a new section 4.1
  "Vorbemerkungen", shifting all of chapter 4 down by one. A stale reference does
  not dangle — it silently redirects to the wrong section, and several of these
  are user-visible in result cards and the PDF export. **No table value changed**;
  see `app/notes/M590-chapter-renumbering.md` for the mapping and what was
  deliberately left alone.
