## What is in this build

The third and — verified this time — actual fix for the spurious update banner.

- **The check switches the banner off, because the library switches it on first.**
  `useRegisterSW` calls `setNeedRefresh(true)` itself and only *then* invokes the
  `onNeedRefresh` callback:

  ```js
  onNeedRefresh() {
    setNeedRefresh(true);   // library, unconditional
    onNeedRefresh?.();      // our callback, afterwards
  }
  ```

  Both previous attempts guarded a `setNeedRefresh(true)` of their own, which the
  library had already performed. They could not suppress anything — 0.1.50 and
  0.1.52 were, in the suppression sense, dead code.

  The check now calls `setNeedRefresh(false)` when the server version matches the
  running build, which is the only direction with an effect.

## How the two earlier attempts survived testing

0.1.50 was "verified" by deploying a *new* version into an open session and
seeing the banner appear — which proves the banner still works for a real
update, not that it is suppressed for a false one. The suppression case was
never actually exercised: it needs the versions to be equal, and both tests had
them differ.

0.1.52 then fixed a real second defect (the leftover-waiting-worker path bypassed
our listener entirely) but inherited the same inverted logic, so it changed which
code ran without changing the outcome.

What settled it was measuring instead of reasoning: on the live 0.1.52, the
running bundle reported 0.1.52, `data/version.json` returned 0.1.52 with a clean
`application/json` content-type, the deployed bundle demonstrably contained the
new guard — and the banner was still up. That combination has only one
explanation, and it is the one above.
