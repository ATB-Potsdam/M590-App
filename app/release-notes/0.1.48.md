## What is in this build

Three defects, all still present in 0.1.47 despite that release being the one
meant to fix this class of problem. Reported from real use: a freshly installed
Android app asked to be updated, and the web app still showed the banner after
loading an older version.

- **A version mismatch at startup no longer produces a banner** (`23b5be4`, web).
  `isStuckOnOldVersion()` bailed out whenever a worker was already `waiting`, on
  the reasoning that the banner would finish the job. That is precisely the
  common case after a deploy, so the mismatch surfaced as "Update verfügbar" on a
  **fresh start** — asking the user to confirm an update to a version they had
  never seen. The rule was already documented in 0.1.47; the code contradicted it.

  Any mismatch now counts, and `forceUpdateAndReload()` resolves it without
  prompting: activate the waiting worker (`SKIP_WAITING` + `controllerchange`,
  with a 3 s timeout) when one is staged, otherwise purge and reload.

- **The native app clears service workers left by older installs** (`23b5be4`,
  native). Not *registering* a worker since 0.1.43 is not the same as not
  *having* one: the Capacitor WebView keeps its data directory across app
  updates, so a worker registered by an install predating that change is still
  active and still serves that install's precached bundle. A freshly installed
  0.1.47 therefore came up as the previous version and asked to update.

  `purgeNativeServiceWorker()` removes any leftover registration and its caches
  on native, reloading only when one was actually controlling the page. Self
  healing: once cleared it stays cleared.

- **No reload loop from the two fixes together** (`23b5be4`, web). The
  successful-load handler cleared the same `sessionStorage` key the
  version-mismatch guard used, so the check re-armed on every pass — reload, load
  fine, clear flag, reload. The load-failure retry and the mismatch guard are now
  separate keys. Measured against a server that never reconciles: **12 reloads
  down to 1**; with matching versions, **no reload at all**.

## What did not change

The update banner still appears for a deploy that lands **mid-session**, on the
web and in an installed PWA — that path runs off the `updatefound` listener and
is untouched. Native returns `null` before the hook runs, so it never shows a
banner at all.

## Rollout note

An installed Android app cannot heal itself from the first two points until it
has been updated once: the fix has to be running to clear the old worker. From
this version onward the situation cannot recur.
